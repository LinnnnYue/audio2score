## 本轮发现并修复的真缺陷（3 个）

### 1. `tempo=0` 导致 ZeroDivisionError 崩溃
- **现象**：传入 `tempo=0` 时任务整体崩溃，UI 只能显示「引擎内部错误」
- **根因**：`pretty_midi.PrettyMIDI(initial_tempo=0)` 内部计算
  `60.0/(initial_tempo * resolution)` 时除零
- **修复**：`pipeline.transcribe` 入口加参数钳制
  - tempo 钳到 [20, 300]，越界时**明确 warning 告知主上**（「已按 20 BPM 处理」）
  - n_peaks 钳到 ≥1
  - onset / pitch_threshold 钳到 [0, 1]
- **位置**：`pipeline.py` 分支之前（**踩坑：初版放在分支之后，Python NameError**）

### 2. 伪造文件被放行
- **现象**：① 纯文本改名 `.mp3` ② `RIFF` 头合法但内容全 0 的 `.wav`
  都能通过 `probe`，UI 显示「0 秒」却允许提交，用户白等一次失败
- **根因**：只查文件体积，不查内容
- **修复**：`format_guard._sniff_magic()` 内容嗅探
- **踩坑实录**：魔数表初版**只比对开头 4 字节** → **m4a 被误伤拦截**！
  MP4 的 `ftyp` box 在**偏移 4~8**（前 4 字节是 box size），不是文件开头。
  而 m4a 正是主上从音乐平台拿音频的高频格式。修正为偏移匹配。
- **双向验证**：真实文件 9/9 零误伤 + 伪造文件 2/2 全拦

### 3. `probe` 返回「可用但时长 0」的中间态
- **修复**：`duration <= 0` 直接判失败，不给中间态

## 本轮修正的测试脚本自身缺陷（4 个，均为误报）

这一条比修产品缺陷更重要：**测试自己有 bug 时，它的「失败」不构成产品缺陷的证据。**

| # | 测试脚本的 bug | 误报原因 | 正解 |
|---|---|---|---|
| 1 | 残留进程断言统计所有 python 进程 | 主上机器常驻 2 个 `pythonw.exe`（19MB/5MB 无窗口应用），与 bridge 无关 | 只统计 `python.exe`（排除 pythonw） |
| 2 | 同上 | **本测试自身就是 python.exe**，统计时自己还活着，必然 +1 | 取**基线差值**，对「自己也在范围内」天然免疫 |
| 3 | 并发断言把 `(path, ok)` 元组喂给 `os.path.isfile` | TypeError 使整条用例失效 | 先解包再断言 |
| 4 | RSS 采样用 `rsplit(",")` 取 tasklist 末列 | `"20,080 K"` 的**千分位逗号成了分隔符**，解析出 80KB | 正则 `"([\d,]+)\s*K"$` |

## 其他已确认的「假警报」（记录以免重犯）

- **MuseScore 全报 rc=1320**：真因是验证脚本在项目根目录跑却用 `../.tmp/`
  相对路径（指向不存在的 `<TMP>`）。**判据：验证失败时先确认验证脚本
  自己没错，再怀疑产物。**
- **分离降级到 HPSS**：真因是 demucs 4.1.0 的 `apply_model()` 无 `ref` 参数
  （3.x 旧签名）。**降级不能吞掉失败原因**，否则表象掩盖真因。
- **Cellar 旋钮与下拉参数双写冲突**：分身自报，实测 `setMode(id)` 是唯一入口，
  属**同一 state 的两个视图**，不成立。
