## 0. 四问直答（TL;DR）

| 主上之问                     | 我的回答                                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------- |
| **1. 研究目的是特化「人声转 MIDI」** | 确认。现有人声路径是 **pYIN 单旋律**（`vocals` / `basic_vocals`），这正是要升级的靶点。GAME 是这一靶点上目前最强的公开方案。                |

| **3. ABC 都做，做成选项**       | A/B 做成**引擎档位**；**C 定案为「歌词输出可选项」**（主上裁定，见 §4.2 / §12）：歌词能标出唱到哪段，演奏更亲和；但它与「用哪种音高」正交，且 ~4 GB 体积（Qwen3-ASR）会毁掉 A/B 的可用性，故**不进主干**，作按需模块。见 §4。 |

**一句话结论**：GAME 卖给虚拟歌姬的是「**表演数据**」，我们要的是「**乐谱**」。中间缺的不是模型，是一层**谱面化**——这才是本项目真正要自己做的部分。

## 1. 现状盘点（新方案必须长在这块地基上）

### 1.1 架构红利：引擎是「模式」的单一真源

```
engine/pipeline.py  describe_modes()  ──下发──▶  bridge.get_modes  ──IPC──▶  前端 ModeSelect.tsx
       ↑ 定义 label / description / hint / separates / tracks / roles / page
```

**前端零硬编码模式文案**。这意味着：**新增人声引擎，前端几乎不用改**——只要在 `describe_modes()` 里多返回条目。这是本次接入最大的成本优势，务必利用。

### 1.2 现有 8 条路径（`Mode`）

| mode                  | page | 标签             | 分离     | 算法             | 轨数   |
| --------------------- | ---- | -------------- | ------ | -------------- | ---- |
| `full_auto`           | 1    | 全自动扒谱（两轨）      | Demucs | CQT 多音高 + pYIN | 2    |
| `accompaniment`       | 1    | 只扒伴奏           | Demucs | CQT 多音高        | 1    |
| `vocals`              | 1    | **只扒人声旋律**     | Demucs | **pYIN 单旋律**   | 1    |
| `basic`               | 1    | 整段直扒（乐器·不分离）   | 无      | CQT 多音高        | 1    |
| `basic_vocals`        | 2    | **单轨直扒（人声旋律）** | 无      | **pYIN 单旋律**   | 1    |
| `basic_accompaniment` | 2    | 单轨直扒（伴奏多音高）    | 无      | CQT 多音高        | 1    |
| `basic_multi`         | 2    | 多轨直扒（逐轨）       | 无      | CQT 逐轨         | 0(多) |
| `pre_separated`       | 2    | 已分离音频直入        | 跳过     | 各轨分别扒          | 2    |

**关键观察**：现有「人声」两条路径（`vocals` / `basic_vocals`）**共用 pYIN**，只有"是否先分离"的区别。主上口中的"人声方案1/2"若照字面做，会和现有语义打架——所以必须先正名（§2）。

### 1.3 交互现状

- 两个功能页：**page 1 歌曲扒谱（先分离）** / **page 2 音频直扒（不分离）**
- 每页各有一个 `ModeSelect` 下拉（自定义浮层，键盘可用，已有空态兜底）+ `ModeNote` 说明条 + `ParamPanel` 参数面板
- `Settings.tsx`（673 行）目前管主题等全局项

⚠️ **「page」这个抽象的隐患**：现在它按「是否需分离」划分（一个技术维度），而**不是**按用户意图划分。加人声方案后，这个抽象会崩——因为你可能既想要"分离+人声"（page 1）又想要"不分离+人声"（page 2）。见 §3.2 裁决。

## 3. 交互设计（我的提案）

### 3.1 设计主张：两轴，而非四选一

```
第一轴 · 扒什么（任务级意图）        第二轴 · 用什么引擎（技术档位，可自动）
┌───────────────┬───────────────┐
│   整曲多轨     │    纯人声      │      → 每个轴下 2~3 个 chips
│  含伴奏·多轨   │  单旋律·特化   │         带体积/算力标签
└───────────────┴───────────────┘
```

**为什么拆两轴（而不是把 4 个选项塞进一个下拉）：**

1. **组合爆炸**。现在若加 SheetSage2（v1 报告 §5.3 提到），单轴会变成 6~8 项，用户要在技术名词里挑。
2. **符合用户心智**。小白的问法是「我要扒人声」，不是「我要 GAME-medium-ONNX」。先问意图，再问档位。
3. **可持续**。以后新增引擎只改第二轴，第一轴稳定。

### 3.2 三个候选方案的裁决（逐条给理由）

| 主上候选          | 我的裁决                         | 理由                                                                                                                                         |
| ------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **下拉菜单**（主界面） | **部分采纳**，但**从下拉升级为 chips**   | 下拉的致命伤：**选项间的差异不可见**，必须点开逐个读才知道"人声方案2"是什么。改成 chips + 一行「体积 · 是否需 GPU」后，差异**一眼可见**。                                                         |
| **设置页统一决定**   | ❌ **不采纳为唯一入口**，降级为「**设默认值**」 | ① 这是**任务级决策**，不是全局偏好——今天扒人声、明天扒伴奏，写死在设置里必然来回跳页。② 一旦写死，主界面**看不到当前实际用的是哪个引擎**，结果不符预期时无从归因（违反"不允许无出路的终态"精神）。                                  |
| **单开一页**      | ❌ **第一步不做**，留作 C 档的未来工作台     | ① 多一页 = 多一次跳转 + 返回态管理 + 打断「拖入即扒」的心流。② 现有 `page` 是按「是否需分离」分的，再开一页会让这个抽象彻底崩掉。③ **但**：C 档（带歌词）需要歌词编辑 + 音高曲线可视化，届时**确实**值得一个独立工作台。→ 作为 v3 演进项。 |

### 3.3 线框（主界面，我建议的形态）

```
┌────────────────────────────────────────────────────────┐
│  扒什么                                                 │
│  ┌──────────────────────┐  ┌──────────────────────┐   │
│  │  ▤  整曲多轨          │  │  ♪  纯人声       NEW │   │
│  │  含伴奏，输出多轨      │  │  单旋律，特化引擎     │   │
│  └──────────────────────┘  └──────────────────────┘   │
├────────────────────────────────────────────────────────┤
│  用什么引擎            [ 自动（推荐）                   │  ← 默认「自动」
│  ○ 标准    ● 高精度    ○ 经典                          │
│   GAME     GAME+RMVPE   pYIN(旧)                       │
│   171MB    ~300MB       0MB · 快                        │
├────────────────────────────────────────────────────────┤
│  [   拖入音频，或点击选择文件   ]                        │
│                                                        │
│  ☐ 顺带跑一个对比版本（同时用另一种引擎，挑更准的那份）    │   ⏸ 已推迟，本阶段不做
└────────────────────────────────────────────────────────┘
```

**三处设计创新（针对小白）：**

1. **「自动（推荐）」为默认 chip** —— 大多数用户不选，程序按音频特征预判（有伴奏残留 → 倾向"整曲多轨"；干净单声 → "纯人声"）。**可覆盖**，满足主上"自行试错对比"。
2. **对比模式（回应议程 #3）** —— 勾选后**一次跑 2 个引擎**，结果卡**并列展示**：音符数 / 音域 / 时长 / 试听按钮。用户不必靠 DAW 判断"哪份更准"。**⏸ 主上已裁定推迟，本阶段不做**（设计保留，随时可启用）。
3. **档位自带体积与算力标签** —— 让"选高精度"这个决定的**代价可见**（否则用户不知道自己在多等什么、多下什么）。

### 3.4 记忆与状态（避免"每次都要选"）

| 状态     | 存放                             | 说明                                     |
| ------ | ------------------------------ | -------------------------------------- |
| 上次用的引擎 | 本地持久化（`onboarding-store` 同类机制） | 下次默认选中                                 |
| 默认引擎   | `Settings.tsx`                 | 可改，覆盖"记忆"                              |
| 引擎可用性  | 引擎下发（`install_status`）         | 未安装的档位**置灰并给一键安装**，不静默消失（红线：不允许无出路的终态） |

## 4. 方案 A / B / C 的落地形态

### 4.1 A 与 B → 引擎档位（同一条轴）

| 档           | 链路                                  | 输出                         | 增量体积     |
| ----------- | ----------------------------------- | -------------------------- | -------- |
| **A · 标准**  | Demucs vocal → **GAME medium ONNX** | MIDI（音符 + 边界）              | +171 MB  |
| **B · 高精度** | A + **RMVPE 音高曲线** → 融合             | MIDI（+ pitch bend / 更准的音高） | +~270 MB |

**A 与 B 的真实差异**（必须让用户看得懂，否则选项无意义）：

|      | A · 标准                         | B · 高精度                       |
| ---- | ------------------------------ | ----------------------------- |
| 音高来源 | GAME 内置 softmax 音高（257-bin 质心） | RMVPE 独立声学曲线 **+** GAME 边界，融合 |
| 强项   | 音符边界准（D3PM 迭代）                 | 音高更贴原唱、**转调/滑音场景**更稳          |
| 适合   | 常规扒旋律谱                         | 翻调、要保留演唱细节                    |
| 代价   | —                              | 多一个模型；两路结果需对齐                 |

### 4.2 C → **定案：歌词作为「输出可选项」保留**

主上裁定：「歌词可以作为输出（可选）项保留，毕竟谱面有歌词有助于知道在哪个部分、哪段了，演奏更亲和。」

**实物验证（主上提供）**：`G:\Lin_File\Documents\曲谱\找名字的人-任素汐\`

| 文件 | 歌词承载 | 数量 |
|---|---|---|
| `找名字的人-小提琴.musicxml` | `<lyric number="1"><syllabic>single</syllabic><text>…</text></lyric>` | **222** |
| `找名字的人-小提琴.mid` | lyric 元事件（`FF 05`） | **222** |
| `找名字的人-钢琴谱.musicxml` | 同上 | **222** |

内容一致，中文按字/词分音节：`Mmm` / `找 什` / `么` / `找` / `双` / `结 实 的` / `鞋 子` / `带` / `上` / `三 五 天` / `的 干` / `粮` …

→ **结论**：「歌词」在本项目链路里**已有先例产物、形态已确定**，不必新造轮子；我们要做的只是把 GAME 链路的输出接到这个**既有形态**上。

**但架构上仍须正交**（不塞进引擎下拉的三条理由）：

1. **体积不在一个量级**：C 的 ~4 GB 主因是 Qwen3-ASR 1.7B。塞进同一下拉，用户会以为"要人声就得 4 GB"，把 A/B 一起劝退。
2. **维度正交**：用户可能"要 B 的音高 + 要歌词"，捆在一个下拉里表达不了。
3. **许可证风险独立**：GAME 是 MIT ✅，但 Qwen3-ASR / HubertFA 各自协议需逐个核查（v1 §7.4 第 6 条）；隔离成可选模块后风险不污染主干。

**形态**：

```
输出  ☐ 生成歌词（输出到 MusicXML <lyric> 与 MIDI lyric 事件）
      ☐ 同时导出 MusicXML
```

**实现分两步（建议）**：

| 步 | 内容 | 代价 |
|---|---|---|
| **P6a · 轻** | 歌词**读入 + 对齐**：用户提供 lrc/txt → 对齐到音符 → 写入 `<lyric>` | 零 ASR 体积 |
| **P6b · 重（可选）** | 接 ASR 自动听写歌词（对齐 Vocal2Midi 的 ASR + TiFA 链路） | ~4 GB |

> **技术风险提示**：C 的重活不是"把歌词写进 MusicXML"（那不难），而是**自动得到准确歌词** —— 需 ASR 听写 + TiFA 逐字对齐。P6a 绕开了这一步，先把形态与对齐做扎实。

## 5. 冗余裁剪：虚拟歌姬 → 人声乐谱（双向清单）

GAME/Vocal2Midi 的**设计目标是给虚拟歌姬（OpenUtau / DiffSinger 等）喂数据**。我们只要「人声 → MIDI 谱」。以下逐项裁决：

### 5.1 砍掉（合成器专属，对乐谱无意义）

| 组件                                | 虚拟歌姬用途          | 裁决                   | 理由                                                     |
| --------------------------------- | --------------- | -------------------- | ------------------------------------------------------ |
| **USTX / UST 导出**                 | OpenUtau 合成工程文件 | ✂️ **砍**             | 我们出 MIDI / MusicXML 给 MuseScore。**可选**保留为隐藏出口，不占主流程。   |
| **歌词 / 音素（phoneme）序列**            | 合成器"唱对字"        | ✂️ **砍**（仅 C 档需要）    | 无合成器 → 音素无意义。歌词文本用 MIDI lyric 事件足矣。                    |
| **ASR（Qwen3-ASR 1.7B）**           | 自动听写歌词          | ✂️ **砍出主干** → 歌词模块按需下载 | **4 GB 整合包的主因**。                                       |
| **TiFA 强制对齐**                     | 音素级时间对齐         | ✂️ **砍** → 仅歌词模块需要     | 只为歌词服务。                                                |
| **呼吸 / 气口（breath）标注**             | 合成器换气           | ✂️ **砍**             | 乐谱无此概念。                                                |
| **滑音 / portamento、颤音（vibrato）曲线** | 合成表现力           | ✂️ **砍→降维**          | 转成谱面的**连音线 / 装饰音**表达，不保留连续曲线（除非用户在 B 档明确要 pitch bend）。 |
| **声码器（SiFiGAN 等）**                | 反向合成音频          | ✂️ **砍**             | 我们不做 TTS。                                              |
| **音库元数据（性别 / 语言 / 音域标签）**         | 合成器选音库          | ✂️ **砍**             | 与扒谱无关。                                                 |

### 5.2 保留（核心价值）

| 组件                        | 保留形态                                         |
| ------------------------- | -------------------------------------------- |
| **D3PM 音符边界检测**           | ✅ 核心——GAME 的全部价值所在                           |
| **GAME 音高估计（257-bin 质心）** | ✅ 保留，**末端离散化**为 MIDI 音高                      |
| **音高曲线（连续 f0，B 档）**       | ✅ 保留 → 映射为 pitch bend 或量化参考                  |
| **能量 / 音量包络**             | 🟡 **部分保留** → 映射为 MIDI **velocity**（谱面的强弱记号） |

### 5.3 ⚠️ 反向补课：合成器不需要、**乐谱必须有**的东西

**这是本方案最容易被忽略、也最致命的一节。** GAME 的输出是「**表演**」（时间贴合音频），我们要的是「**乐谱**」（可读、可演奏）。缺口：

| 缺口              | 为什么缺                                   | 我们必须补什么                                                                                      |
| --------------- | -------------------------------------- | -------------------------------------------------------------------------------------------- |
| **BPM**         | GAME **不输出**（v1 报告 §7.4 第 2 条）         | `midi_post.py` 侧补测速，或让用户填（`ParamPanel` 已有 BPM 字段 ✅）                                          |
| **拍号 / 小节线**    | 同上                                     | 测速后推导；不确定时给"无小节"降级                                                                           |
| **调号（fifths）**  | GAME 无语境                               | 调性推断（音高集合 → 最可能调号）。⚠️ memory 链路 A 已有教训：**升降号必须按 fifths 推导，写死必错**                             |
| **量化到节拍网格**     | 评论区实锤：GAME 默认参数有「**杂拍、一音切两段、连奏两音连一段**」 | 新增**谱面整理层**（§6.2）——Vocal2Midi 用"智能节奏对齐"一笔带过，我们必须做扎实                                          |
| **MusicXML 输出** | Vocal2Midi 只出 MIDI / USTX              | 我们最终要给 MuseScore → 必须出 MusicXML。⚠️ **DTD 子元素顺序红线**（`notations` 必须在 `staff` 之后），否则 rc=139 段错误 |
| **tie / 连音线**   | MIDI 无"跨小节同音"概念                        | 拆小节时自动生成 tie。⚠️ 同上 DTD 顺序                                                                    |

> **核心判断**：**GAME 解决问题的一半（"听到什么音、什么时候"），另一半（"这些音在谱面上怎么记"）得我们自己补。** 主上看到的"转换特别精准"，是 GAME 那一半做得好；而"能不能直接给老公拉"，取决于我们补的后一半。

## 6. 架构设计（落在现有代码结构上）

### 6.1 目录与职责

```
engine/
  pipeline.py              # 调度器（现有）：Mode 注册表 + 分派

### 6.2 谱面化层（`scoreify.py`）—— 本项目自研的核心

```
GAME 原始输出                      谱面化                       产物
─────────────────────────────────────────────────────────────────────
notes: [{onset, offset, f0}]  →  ① 离散化（f0 → 半音）       →  MIDI note
boundaries                   →  ② 调性推断（→ fifths）      →  调号
（无 BPM / 拍号）             →  ③ 测速 / 用户填 BPM         →  拍号·小节
                             →  ④ 量化到网格（可调强度）     →  对齐的时值
                             →  ⑤ 拆分跨小节 → tie          →  连音线
                             →  ⑥ velocity（由能量映射）     →  力度
                             →  ⑦ 导出 MIDI + MusicXML     →  给 MuseScore
```

**④ 量化强度：滑杆 + 三档数值预设**（主上裁定）

- **滑杆**：连续可调，给高手微操（0 = 完全贴音频，1 = 完全贴网格）
- **三档预设按钮**（一键跳值，给小白）：

| 预设 | 取值来源 | 效果 |
|---|---|---|
| `贴原唱` | **GAME 原预设** | 弱量化：时间最贴音频，但可能有杂拍/一音切两段 |
| `标准谱面` | **折中值（默认）** | 日常用，兼顾贴合与可读 |
| `规范谱面` | **SheetSage2 数值** | 强量化到栅格：音符最纯，但偏离原唱 |

→ 这正好把 v1 报告 §5.3 那条 **GAME vs SheetSage2** 的取舍，从"二选一的路线之争"**变成用户可调的旋钮**：一键切换取向，滑杆再细调。**这是本方案我最推荐的一个设计。**

## 7. 安装档位重构（本次最实的体验改善）

### 7.1 现状问题

现有三档：`basic` ~200 MB / `full` ~5.1 GB（推荐）/ `mcp` ~5.1 GB。

**问题**：只想扒人声的用户，被迫下 **5.1 GB**——因为推荐档 = full = 含 torch CUDA + Demucs。

### 7.2 ★ 关键洞察：**人声档可以脱离 torch**

- GAME 走 **ONNX Runtime**，**不需要 PyTorch**
- RMVPE 同样可转 ONNX
- → **"人声·纯 ONNX"路径约 400 MB**，比 5.1 GB **小 12 倍**

**但有一个分叉必须点明：**

| 场景                    | 是否需要 Demucs         | 体积            |
| --------------------- | ------------------- | ------------- |
| 用户**已有人声轨**（清唱 / 已分离） | ❌ 不需要               | **~400 MB** ✅ |
| 用户给的是**混音**，需自动分离人声   | ✅ 需要 torch + Demucs | ~5.2 GB       |

### 7.3 建议的档位结构（预置组合 + 能力模块）

```
核心（必装，~50MB）       壳 + Python + 基础音频库
────────────────────────────────────────────────
能力模块（按需，用时下载）
  ├ 多轨·快速       librosa 系              已含在核心
  ├ 多轨·精准       torch CUDA + Demucs      ~5.0 GB
  ├ 人声·标准       onnxruntime + GAME 171MB ~400 MB   ← 不含 torch！
  ├ 人声·高精度     + RMVPE                  ~550 MB
  └ 歌词（C 档）    + Qwen3-ASR + TiFA       ~4.4 GB   ← 明确标注
```

**UI 上仍保留 `basic / full / mcp` 三个"预置组合"**&#x7ED9;不愿细想的用户，另给"自定义"让进阶用户按模块勾选。**同一份真源**（`bootstrap.py` 的 TIER 定义 → 下发），不改现有"前端不硬编码档位文案"的约定。

> ⚠️ 待验证：ONNX Runtime 在 Windows + 目标用户机的兼容性与 CPU 推理耗时（v1 报告 §7.4 第 3 条）。若 CPU 太慢，需给「人声·标准（GPU）」变体。

## 附录 A：进度条「百分比直达 100%」缺陷（已修复 · 2026-10-07）

**主上反馈**：运行时候的进度条百分比会直接到 100，不太准确。

**根因（两处重叠失误）**：

1. `pipeline.py` 把 `separator` 的**阶段内** 0~1 进度**直连**给全局进度回调 → 分离完成时它推的 `1.0` 被当成全局 100%。
2. 同一文件另有一行 `_mono("prepare", 1.0, "准备完成")` 把**阶段结束**误写成**全局 1.0**。

而 `_mono` 是**单调函数**（只增不减，用于防止进度条倒退），因此一旦到 1.0，**后续所有真实进度被永久钳死** → 从分离完成起进度条就卡在 100%。

**修复**：建立**全流程一套刻度**，任何模块只准推自己的阶段内 0~1，由 adapter 换算：

| 阶段 | 全局区间 |
|---|---|
| prepare | 0.00 → 0.05 |
| separate（Demucs） | 0.05 → 0.50 |
| spectrum / track | 0.50 → 0.90 |
| export | 0.90 → 1.00 |

（无分离的模式：`track_lo` 自动下移，跳过并不存在的「分离」区间。）

**验证**（`test_progress_monotonic.py`，新增判据「满格只允许出现在最后一个进度事件」）：

```
